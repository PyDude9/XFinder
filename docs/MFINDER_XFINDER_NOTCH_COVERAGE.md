# XFinder Notch / Dynamic Island — feature coverage against the OneNotch product spec

**Purpose:** Compare the 28 feature groups in the supplied Notch/Dynamic Island specification with XFinder's current source structure. This is a source-level inventory and product gap map, not a claim that the reference app or XFinder was live-tested.

**Source baseline:** `a48e274` (`main`, 2026-11-06); **notch opening update:** XF-T36 working tree. **No installed-app behavior was verified for this review.** File presence and UI strings establish source representation, not that permissions, OS services, or external integrations currently work.

## Reading the status

- **In source:** a corresponding XFinder surface/engine is present in the inspected checkout.
- **Partial:** a related behavior exists, but the specification asks for more or the contract is not established.
- **No source evidence:** a source scan did not find a dedicated implementation. This is not proof that no indirect/experimental implementation exists.
- **App-level, not a notch page:** the feature may be reachable elsewhere in XFinder; the supplied spec does not require every feature to be crammed into the compact notch.
- **Not live-verified:** runtime, permission, hardware, and accessibility behavior still needs testing in the installed app.

## Product boundary

The specification describes a whole productivity utility whose notch is one entry point. XFinder's notch is currently a compact hub and activity surface, not a container for every editor, system utility, or permission flow. Keep the camera-attached surface focused on glanceable status and short actions. Route work needing space to the existing library, detail pane, or a separate editor/window, and return users to their original page and selection.

Current page model in source: `files`, `clipboard`, `nowPlaying`, `agents`, `calendar`, `timer`, and `aiUsage`. The default ordering is defined in `NotchPages.defaultOrder`; pages can be reordered and hidden while retaining at least one. The surface machine has `collapsed`, `peek`, `expanded(page)`, and transient `activity` states. Its current triggers include click/reveal, file drag, drag-shake, hover, and page swipe. This is materially aligned with the core shell proposal, but it is not the entire proposed display/fullscreen policy.

## Core notch comparison: proposed behavior vs. observed source

| Behavior from spec | Source-level status | User-visible implication / next review |
|---|---|---|
| Closed, peek, expanded, live activity | Present in the surface state machine and view. | Review each state in the installed app, including return to prior page after a notice. |
| Physical notch and ordinary-display pill | Geometry and `notch.pillOnPlainScreens` setting exist. | Current selection is screen-under-pointer/open context; no user-facing preferred/all/active display policy was found. |
| Click, hover, activity-based opening | Source has separate `notch.hoverOpens` and XF-T36 `notch.clickOpens` policies. Click defaults to Files; hover behavior remains independent. | Click offers fixed page, last-used page, or activity choice. Explicit destinations win. Verify pointer focus and popover exit behavior live. |
| Page navigation and hidden pages | Seven pages, order/visibility, horizontal two-finger tab swipe. | No evidence of customizable page dots/toolbar controls beyond current surface. Keyboard/VoiceOver route needs live audit. |
| Fullscreen policy | No user-facing policy found in the inspected notch settings/controller. | Future task should define hide/show behavior and guarantee access to active Stop controls. |
| Capture privacy | One `notch.hideFromCapture` switch maps to window sharing behavior. | This does not prove exclusion from every screenshot, recorder, meeting app, or system capture path. Keep platform limits visible. |
| Multiple activities and interruption order | Activity machinery exists. | The full proposed priority/deduplication/history model is not established. Verify that an approval/session cannot be replaced by passive media updates. |
| Open large editors/libraries | App has separate clipboard/settings/capture windows. | Preserve origin page, selection, filters and scroll position on open/close; test each route. |

## Recommended update sequence

1. **Close remaining core shell contract gaps:** decide the display-target policy and fullscreen-visibility policy. These affect every page and active recording/Stop access. Keep the current pointer-selected behavior as the fallback until a policy is explicitly set.
2. **Verify current notch journeys in the installed app:** deliberate-open page choice, hidden-page routing, explicit destination routing, page swipe, hover while composing, child popover/outside click, screen disconnect, fullscreen, capture visibility, and permission revocation.
3. **Tighten existing notch pages against the supplied states:** clipboard and paste queue; file tray mixed batches/cancellation; Calendar permission and refresh; timer sleep/wake; AI session expiry/approval and incomplete usage.
4. **Keep app-level editors separate:** screenshots, OCR, markup, translation, smart selection, Keep Awake, monitor, snap and menu-bar organization remain in their existing pages/windows, with notch status/actions only where useful.
5. **Create separate specs before adding absent feature families:** local tasks, clipboard-to-agent MCP, image combine, screen recording/video editing, eye breaks, and presenter/teleprompter. Each needs its own privacy, permission, persistence, cancellation, and recovery contract.

## Future acceptance for this comparison

- Given a proposed behavior and a source component, when the auditor reviews the feature, then the matrix records whether it is in source, partial, absent from the scan, or live-unverified; a filename alone never proves a working service.
- Given a feature that needs a large editor, when launched from the notch, then it opens the owning app-level window and returns to the prior notch page/selection when closed.
- Given a group marked “No source evidence,” when the project/build-target audit is complete, then the task is either reclassified with concrete source evidence or kept as an explicitly unimplemented feature; it is not silently claimed as available.
- Given an active recording/approval/timer and a passive activity update, when both are present, then the action needing attention remains reachable and the event policy is deterministic.

## Not live-verified

This comparison did not install or launch XFinder. It did not verify the user's actual permissions, media sources, display matrix, VoiceOver, fullscreen behavior, screen capture exclusion, filesystem access, calendar access, audio routing, or external provider state. The matrix is a planning aid based on source paths at `a48e274`; it must be updated when later code or live review changes these facts.
